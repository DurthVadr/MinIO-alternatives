# Contributing

The most useful thing you can send is **a result set from hardware that is not
an Apple M1 with 8 GB of RAM**, which is the only machine this study has run on.

That limitation is structural rather than incidental, and it shapes how the
repository is laid out: every result is stamped with an automatically collected
hardware profile and filed under `results/<profile_id>/`, so results from
different machines sit side by side instead of overwriting one another. Nothing
about the harness assumes there is one of them.

## Contributing results

You need Docker and a Python 3 with PyYAML. For scale: on the reference
machine 29 measured runs took 1.7 hours end to end, a median run being 87
seconds of measurement plus about 11 seconds of stack lifecycle. The full
192-run matrix is most of a day; `--quick` is 24 runs.

```sh
git clone <this repo> && cd <this repo>
python -m venv .venv && .venv/bin/pip install -r requirements-dev.txt

bench/lock-images.sh          # confirm the pinned digests still resolve
bench/hwprofile.sh            # see the profile_id your results will land under

bench/run.sh --dry-run        # the matrix this machine would run
bench/run.sh                  # or --quick for one round, three profiles
```

Then the two suites that write their own artefacts:

```sh
.venv/bin/python -m pytest conformance -q
BENCH_WRITE_RESULTS=1 .venv/bin/python -m pytest tests/test_durability.py -q
```

Both need the whole file to run. `pytest conformance -k sse` merges its handful
of cells into whatever was already in `conformance.json`, which is fine while
you are iterating and wrong to publish — the suite prints a warning when the
session was filtered.

Finally regenerate the report and open a pull request:

```sh
bench/make_results.py
git add results/<your-profile-id> RESULTS.md
```

### What to include, and what not to

Commit the whole `results/<your-profile-id>/` directory: `conformance.json`,
`durability.json`, `hardware-profile.json`, and everything under `raw/` —
the result JSON, the telemetry CSV and the warp log for each run.

**Do not commit warp's per-request benchdata.** `results/**/*.benchdata.*` is
gitignored on purpose, not by oversight. A full matrix produces around 300 MB
of it, which would make this contribution workflow unusable within a few
result sets. Every result file records its benchdata's byte count and SHA256,
so a specific run can still be identified and re-analysed by whoever has the
file.

### If a run fails, send it anyway

A `failed` or `suspect` run is data. SeaweedFS having no 20 MiB number on this
machine is one of the study's findings, and it only became one because the
absence was recorded rather than quietly dropped.

What is *not* useful is a run whose conditions differ from the matrix — a
different memory budget, a tuned configuration, a different warp version.
Those belong in `results/<profile_id>/diagnostics/`, with a `why` field saying
what was changed and a `not_a_benchmark_result: true` flag.
`bench/make_results.py` renders that directory in its own section, explicitly
marked as not comparable. See `bench/diagnose-seaweedfs-memory.sh` for the
shape.

## Working on the harness

```sh
.venv/bin/python -m pytest tests -q
```

111 tests. Many of them shell out to Docker — `test_hwprofile.py` and
`test_run_orchestrator.py` will fail outright if the daemon is not running,
which is a missing dependency rather than a regression.

`tests/test_durability.py` and `tests/test_smoke_roundtrip.py` bring real
stacks up and take minutes. Do not run the suite while a benchmark is in
flight: both use the same ports, container names and Docker network, and the
two will fight.

### House rules

**Every published claim comes from a file.** RESULTS.md is generated by
`bench/make_results.py` and is never hand-edited — `tests/test_make_results.py`
fails if the committed copy has drifted from the data. If you want to say
something in it, make the generator say it from a value that is actually
recorded.

**Every image is pinned by digest.** `tests/test_images_lock.py` enforces this
across `images.lock`, `compose/*.yaml` and `bench/*.sh`, including helper
images. A floating tag can be repointed mid-study with nothing recording it.

**Never interpolate a shell value into Python source.** Quote your heredocs
(`<<'PY'`) and pass values through the environment or argv. `bench/hwprofile.sh`
did the other thing once, and a backtick in a comment executed a command.

**A test that fails without reaching a verdict records `error`, not a status.**
Conformance cells are public claims about named products. Deriving one from a
harness failure is how a bug becomes an accusation.

## Adding a system

Five places, and the tests will tell you if you miss one:

1. `images.lock` — a `ref`, a `sha256:` digest and a `note`.
2. `compose/<system>.yaml` — a stack with both a `c1` profile (single device,
   no redundancy) and a `c2` profile (survives the loss of exactly one device).
   The 6 CPU / 2048m budget is declared per file, via that file's own YAML
   anchors; `compose/_common.yaml` carries only the shared network, because
   Compose's `include:` cannot resolve an anchor across files.
3. `bench/stack.sh` — add the name to `SYSTEMS`.
4. `bench/run.sh` — add the name to `ALL_SYSTEMS`.
5. `conformance/conftest.py` — add the name to `KNOWN_SYSTEMS`.

The c2 configuration is the load-bearing one. It has to survive one device
loss and no more, because that is the axis the whole comparison holds equal
(see [METHODOLOGY.md](METHODOLOGY.md) §3). If your system needs a non-default
setting to run that way, record it as a configuration caveat in
`tests/test_durability.py` so the disclosure travels inside `durability.json`
rather than living in prose someone can drop.

## Adding a conformance behaviour

Add a test to `conformance/test_s3_conformance.py`. It must record a status on
every behavioural path rather than only asserting — a bare `assert` is
reserved for harness invariants, where `error` is the right answer.

Pick the status carefully. The distinction that earns this suite its keep is
`accepted_not_enforced` versus `not_implemented`: a call that returns success
without applying the guarantee it implies is a different and more dangerous
finding than a call that is honestly missing. If you use `not_exercisable`, the
`reason` field is mandatory, and it must say whether the system refused
correctly (`conformant_refusal`) or the deployment lacked something the feature
needs (`missing_prerequisite`).

Make the prerequisite rule system-agnostic. The SSE-C-over-HTTP check reads the
endpoint scheme, not the system name, so it cannot quietly become an exemption
for one product.

## Reporting something wrong in the results

Open an issue with the file and the cell. Every number and every status in
RESULTS.md traces back to a JSON file under `results/`, and each carries the
detail line recorded at the moment it was produced, so a disagreement can be
settled against the evidence rather than against a recollection.

If a published claim turns out to be wrong, the fix is to correct the data and
regenerate — not to edit the prose around it.
