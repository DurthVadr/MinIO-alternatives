## Durability

Not asserted from configuration. For every system an object is written, a device is then actually destroyed, and the object is read back and compared byte for byte.

| System | Mechanism | One device lost | Usable space |
| --- | --- | --- | ---: |
| minio | erasure coding, 4 drives, parity 1 | survived | 0.7497 |
| silo | erasure coding, 4 drives, parity 1 | survived | 0.7497 |
| rustfs | erasure coding, 4 drives, parity 1 | survived | 0.7495 |
| seaweedfs | replication 001, 2 copies across 4 volume servers | survived | 0.5000 |

`Usable space` is measured, not derived: a known volume of objects is written and the bytes that land on the backing devices are counted. It is a result, not a control.

**Fault tolerance is the axis held equal, and storage efficiency is what it costs.** Erasure coding and replication cannot be equalised on both at once. Every system here is configured to survive the loss of exactly one device, and the space that costs is the number in the last column: for the same guarantee, erasure coding leaves about 75% of raw capacity usable and 2-copy replication leaves 50%.

### Past the redundancy limit

A negative control: enough devices are destroyed that the data cannot be reconstructed, and the read is confirmed to fail. Without it, a passing durability test says nothing about whether the test can fail at all.

Reads are then sampled on a fixed schedule — **t=0 is the moment the fault-injection command returns**, followed by samples at 0.25, 0.5, 1, 2, 4 and 8 seconds. The counts below describe that schedule, not observed frequencies: a behaviour confined to a sub-second window appears once because only the earliest samples land inside it.

| System | What was destroyed | Read failed | Sampled outcomes |
| --- | --- | --- | --- |
| minio | /data1, /data2 wiped as well (parity 1 cannot cover 2 lost drives) | yes | `HTTP 404 / NoSuchBucket` ×2, `HTTP 503 / SlowDownRead` ×5 |
| silo | /data1, /data2 wiped as well (parity 1 cannot cover 2 lost drives) | yes | `HTTP 404 / NoSuchBucket` ×2, `HTTP 503 / SlowDownRead` ×5 |
| rustfs | /data1, /data2 wiped as well (parity 1 cannot cover 2 lost drives) | yes | `HTTP 200 / ResponseStreamingError` ×1, `HTTP 200 / SlowDown` ×1, `HTTP 503 / SlowDown` ×5 |
| seaweedfs | every server holding volume 8 stopped (bench-swfs-vol0, bench-swfs-vol1, including bench-swfs-vol1) | yes | `HTTP 500 / ProtocolError` ×7 |

None of the four fails cleanly in the first moments after the fault. The transient shapes differ — a wrong error code, a `Content-Length` that does not match the body, an error body that is not S3 XML — and they are worth knowing if a client of yours retries on them.

### Configuration caveats

Settings that had to be changed to get a comparable measurement, recorded here rather than in prose so they travel with the data.

**rustfs** — `RUSTFS_UNSAFE_BYPASS_DISK_CHECK=true`

- *Effect on the comparison:* Equalises rather than relaxes. The alternatives were to drop RustFS from config 2, or to give it four real devices the other three did not get; both would have made the comparison less fair, not more.
- *Finding:* RustFS is the only one of the four that treats a shared physical device under erasure coding as a startup error rather than a warning or silence. It is also the youngest of the four (rc). A maturity row built from this data should say so in both directions.
- *Also required:* user: root -- the image runs as uid 10001 and only /data is pre-owned by it, so fresh /data0../data3 mounts are root-owned and the server dies with 'Io error: Permission denied (os error 13)'. compose/minio.yaml needs the same workaround.

## Performance

### How to read this section

The design called for three interleaved rounds and a median. **What exists is round 1, once.** Warm-up and ordering effects are therefore uncontrolled, and the data contains direct evidence that they matter: on `bigdata-get`, both Silo and RustFS measured *faster* in their redundant configuration than in their single-device one. Erasure coding cannot make a read cheaper, so something other than the storage configuration is moving those numbers by that much.

Read the tables comparatively within a row group, treat differences under roughly 20% as noise, and do not quote any single number as a property of the software. Absolute values belong to this hardware.

Latency is the end-to-end request duration for the measured operation, in milliseconds, as `p50 / p99`. It is computed from warp's per-request records, not by averaging its 10-second window summaries — percentiles cannot be averaged across windows, and doing it inflated the median of one run by 3.8x before it was caught.

`errors` is warp's own error counter. A run can carry a handful of them and still read `ok`: the error-rate checks have thresholds, and warp counts some of its own record-keeping faults there too. A run whose errors mattered appears under [Runs that are not clean](#runs-that-are-not-clean).

An empty cell is a hole in the matrix, not a zero. `*no result*` means the combination was never run; a row with a `failed` status means it was run and did not produce a usable measurement.

## Reproducing this

```sh
python -m venv .venv && .venv/bin/pip install -r requirements-dev.txt
bench/lock-images.sh               # re-resolve digests, exit 1 on drift
bench/run.sh                       # the full matrix
bench/make_results.py              # regenerate this file
```

`bench/run.sh` is resumable: a cell that already has a result file is skipped, so an interrupted matrix continues rather than restarts.

Results from other hardware are welcome and land in their own `results/<profile-id>/` directory alongside `apple-m1-8gb-darwin`. See [CONTRIBUTING.md](CONTRIBUTING.md).
